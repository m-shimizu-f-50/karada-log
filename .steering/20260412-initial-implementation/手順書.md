## セクション 2: バックエンド初期化

### 全体の流れ（概要）

「Node.js 上で動く API サーバーを Hono というフレームワークで作り、起動確認するまで」の作業。

```
backend/
├── package.json        … 依存パッケージの管理
├── tsconfig.json       … TypeScript の設定
├── .env / .env.example … 環境変数
└── src/
    └── index.ts        … サーバーのエントリーポイント（起動ファイル）
```

---

### 実施したこと

#### 1. `package.json` を作成した（`npm init -y`）

Node.js プロジェクトの設定ファイル。依存パッケージの一覧やスクリプトを管理する。
`-y` オプションで質問なしにデフォルト値で作成した。

#### 2. パッケージをインストールした

```bash
npm install hono @hono/node-server   # Web フレームワーク
npm install prisma @prisma/client    # DB 操作ライブラリ（セクション3で使用）
npm install zod                      # バリデーションライブラリ
npm install -D typescript @types/node tsx
```

| パッケージ | 役割 |
|---|---|
| `hono` | Web フレームワーク本体。ルーティング・ミドルウェアを定義する |
| `@hono/node-server` | Hono を Node.js で動かすためのアダプター |
| `zod` | リクエストの値が正しい形式かチェックするライブラリ |
| `typescript` | TypeScript コンパイラ（開発時のみ） |
| `tsx` | TypeScript ファイルを直接実行するツール（`tsc` でコンパイルせずに `ts` を動かせる） |

#### 3. `tsconfig.json` を作成した

TypeScript の動作を設定するファイル。主な設定：

```json
{
  "compilerOptions": {
    "target": "ES2022",          // 出力する JavaScript のバージョン
    "module": "NodeNext",        // Node.js のモジュール形式（ESM）
    "moduleResolution": "NodeNext",
    "outDir": "./dist",          // コンパイル後のファイルの出力先
    "rootDir": "./src",          // TypeScript ソースファイルの場所
    "strict": true               // 厳格な型チェックを有効化
  }
}
```

#### 4. `package.json` にスクリプトを追加した

```json
{
  "scripts": {
    "dev": "tsx watch src/index.ts",   // 開発用（ファイル変更で自動再起動）
    "build": "tsc",                    // TypeScript → JavaScript にコンパイル
    "start": "node dist/index.js",     // 本番用（コンパイル済みファイルを実行）
    "type-check": "tsc --noEmit"       // 型エラーチェックのみ（コンパイルはしない）
  }
}
```

`tsx watch` の `watch` オプションでファイルを監視し、保存するたびに自動でサーバーが再起動する（開発時の利便性向上）。

#### 5. `src/index.ts` を作成した

Hono アプリのエントリーポイント（起動ファイル）。

```typescript
import { serve } from "@hono/node-server";
import { Hono } from "hono";
import { cors } from "hono/cors";

const app = new Hono();

// CORS ミドルウェアの設定
app.use("*", cors({
  origin: process.env.FRONTEND_URL ?? "http://localhost:3000",
  credentials: true,
}));

// /health エンドポイント（サーバーの死活確認用）
app.get("/health", (c) => {
  return c.json({ status: "ok" });
});

// サーバー起動
const port = Number(process.env.PORT) || 8080;
serve({ fetch: app.fetch, port }, () => {
  console.log(`Server running on http://localhost:${port}`);
});
```

**CORS（Cross-Origin Resource Sharing）とは？**
ブラウザは「異なるドメイン（オリジン）への通信」をデフォルトでブロックする。
フロントエンド（`localhost:3000`）からバックエンド（`localhost:8080`）に通信するには、バックエンド側で「このオリジンからの通信を許可する」と明示する必要がある。それが CORS ミドルウェアの役割。

`credentials: true` はクッキーや認証ヘッダーを含む通信を許可する設定（ログイン機能に必要）。

**`/health` エンドポイントとは？**
サーバーが正常に動いているか確認するためだけのエンドポイント。
`{ "status": "ok" }` を返すだけ。CI/CD やデプロイ後の動作確認に使う。

#### 6. `.env` / `.env.example` を作成した

```
DATABASE_URL=...    # データベース接続先（セクション3で設定）
AUTH_SECRET=...     # JWT 署名用の秘密鍵（セクション4で設定）
PORT=8080           # サーバーが待ち受けるポート番号
FRONTEND_URL=http://localhost:3000  # CORS で許可するフロントエンドの URL
```

`.env` は実際の値を書く機密ファイルで Git に含めない。
`.env.example` はキーの一覧だけを書いたサンプルファイルで Git に含める（チームへの共有用）。

---

### ポイント・気づき

- **フレームワークとは**: Express.js や Hono のような Web フレームワークは「URL ごとに処理を振り分ける仕組み（ルーティング）」を簡単に書けるようにするライブラリ。フレームワークなしだと Node.js 標準の `http` モジュールで全部自分で書く必要がある
- **ミドルウェアとは**: リクエストを受け取ってから、実際の処理（ルートハンドラ）が実行される前後に挟める処理のこと。CORS 設定・認証チェック・ログ出力などに使う
- **環境変数とは**: ポート番号やパスワードのような「環境によって変わる値」や「コードに直書きしたくない秘密の値」を外部から渡す仕組み。`process.env.変数名` でアクセスできる

---

### 確認したこと

- `npm run dev` でサーバーが起動し、`http://localhost:8080/health` にアクセスして `{"status":"ok"}` が返ることを確認

## セクション 3: DB設計・Prisma セットアップ

### 全体の流れ（概要）

「データベースのテーブル構造をコードで定義し、実際のデータベースに反映させる」作業。

```
schema.prisma（設計図）
    ↓ prisma generate
Prisma Client（TypeScript の型付き DB 操作ライブラリ）
    ↓ SQL 生成・実行
Supabase（実際のデータベース）のテーブル
```

---

### 実施したこと

#### 1. `prisma/schema.prisma` を作成した

Prisma のスキーマファイルは「どんなテーブルが必要か」を記述する設計図。
SQL を直接書かずに、TypeScript に近い記法でテーブル定義を書ける。

作成したモデル（テーブル）は7つ：

| モデル名 | テーブル名 | 役割 |
|---|---|---|
| `User` | `users` | ユーザー情報（メール・名前・画像） |
| `Account` | `accounts` | OAuth 連携情報（NextAuth.js が必須で使う） |
| `Session` | `sessions` | ログインセッション管理（NextAuth.js が必須で使う） |
| `WeightRecord` | `weight_records` | 体重の記録（日付・体重） |
| `WeightGoal` | `weight_goals` | 目標体重 |
| `MealRecord` | `meal_records` | 食事の記録（食品名・カロリー・朝昼夜） |
| `ExerciseRecord` | `exercise_records` | 運動の記録（種目・時間・消費カロリー） |

重要な設定として `WeightRecord` に `@@unique([userId, date])` を付けた。
これは「同じユーザーが同じ日に体重を2件登録できない」という制約。
（同じ日に体重を登録した場合は上書きする仕様のため）

#### 2. `prisma.config.ts` を作成した

Prisma 7 から `schema.prisma` 内に接続 URL を書く方法が廃止された。
代わりに `prisma.config.ts` というファイルに接続先情報を書く。

```typescript
// prisma.config.ts
import { defineConfig } from 'prisma/config'
import { config } from 'dotenv'

config()  // .env ファイルを読み込む

export default defineConfig({
  datasource: {
    url: process.env.DATABASE_URL!,  // .env の DATABASE_URL を使う
  },
})
```

#### 3. Supabase の SQL エディタでテーブルを作成した

通常は `npx prisma migrate dev` コマンド1つでテーブルが作られる。
しかしこの開発環境（DevContainer）はセキュリティ上の制限でポート 5432 への外部接続ができないため、コマンドが失敗した。

代替手順として：
1. `npx prisma migrate diff --from-empty --to-schema prisma/schema.prisma --script` コマンドで SQL を生成した
2. 生成された SQL を Supabase ダッシュボードの「SQL Editor」に貼り付けて実行した

`migrate diff` コマンドは「空のデータベースと、この schema.prisma の差分を SQL で出力する」という意味。
これにより接続不要で CREATE TABLE 文が生成できる。

#### 4. `npx prisma generate` を実行した

Prisma Client（TypeScript でデータベースを操作するためのライブラリ）を生成するコマンド。
このコマンドを実行すると、`node_modules/@prisma/client` に型付きの DB 操作関数が自動生成される。

例えば以下のように使える：
```typescript
// ユーザー一覧取得
const users = await prisma.user.findMany()

// 体重記録を作成
const record = await prisma.weightRecord.create({
  data: { userId: '...', date: new Date(), weight: 68.5 }
})
```

#### 5. `src/lib/db.ts` を作成した

Prisma Client のシングルトン（アプリ全体で1つのインスタンスを共有する仕組み）を定義するファイル。

```typescript
// src/lib/db.ts
import { PrismaClient } from '@prisma/client'

const globalForPrisma = globalThis as unknown as { prisma: PrismaClient }

export const prisma =
  globalForPrisma.prisma ?? new PrismaClient()

if (process.env.NODE_ENV !== 'production') {
  globalForPrisma.prisma = prisma
}
```

**なぜシングルトンが必要か？**
`new PrismaClient()` を呼ぶたびに新しい DB 接続が作られる。
開発中はファイル変更のたびにコードが再読み込みされるため、
毎回 `new PrismaClient()` すると接続が増えすぎてエラーになる。
グローバル変数にキャッシュしておくことで接続の使い回しができる。

---

### ハマった点

- **Prisma 7 の設定方法が変わっていた**: `schema.prisma` に `url = env("DATABASE_URL")` と書く旧来の方法が廃止されており、`prisma.config.ts` が必要になった
- **DevContainer からポート 5432 への接続がブロックされていた**: `migrate dev` が使えず、SQL を手動で Supabase SQL エディタに貼り付ける方法で対応した
- **Supabase の RLS 警告**: テーブル作成時に「RLS が無効」という警告が出たが、このプロジェクトはバックエンド API 経由でアクセスするため無視して問題ない

---

### 確認したこと

- Supabase の「Table Editor」で7つのテーブルが作成されていることを確認できる
- `npx prisma generate` が成功し、Prisma Client が生成された

## セクション 4: 認証（NextAuth.js）

### 全体の流れ（概要）

「Google アカウントでログインできるようにして、ログインしていないユーザーを弾く仕組みを作る」作業。

```
① ユーザーが「Googleでログイン」をクリック
        ↓
② Google の認証画面にリダイレクト
        ↓
③ ユーザーが Google で許可
        ↓
④ NextAuth.js がユーザー情報を受け取り、JWT（暗号化されたトークン）を発行
        ↓
⑤ JWT がブラウザのクッキーに保存される
        ↓
⑥ 以降のリクエストはクッキーの JWT を確認して「ログイン済み」と判断
        ↓
⑦ バックエンド API にリクエストを送るときは JWT を一緒に送り、バックエンドで検証
```

---

### OAuth 2.0 とは？

パスワードを預からずに「Google が本人確認済み」という情報だけを受け取る仕組み。

```
アプリ ──「このユーザーを確認して」──▶ Google
       ◀── 「確認済みです。情報はこちら」── Google
```

アプリはパスワードを知らなくていい。Google が代わりに確認してくれる。

---

### JWT（JSON Web Token）とは？

ユーザー情報を暗号化してひとつの文字列にまとめたもの。

```
eyJhbGciOiJkaXIiLCJlbmMiOiJBMjU2Q0JDLUhTNTEyIn0...（長い文字列）
```

この文字列の中には `{ email: "...", name: "...", exp: 期限 }` などの情報が暗号化されて入っている。
`AUTH_SECRET` という秘密鍵がないと復号できないため、改ざんすることができない。

---

### 実施したこと・作成したファイル

---

#### 1. `frontend/.env.local` — 認証に必要な環境変数

```
AUTH_SECRET=...         ← JWT の暗号化・復号に使う秘密鍵（ランダム生成）
AUTH_GOOGLE_ID=...      ← Google Cloud で発行したクライアント ID
AUTH_GOOGLE_SECRET=...  ← Google Cloud で発行したクライアントシークレット
NEXT_PUBLIC_API_URL=... ← バックエンド API の URL
```

`AUTH_SECRET` はフロントエンドとバックエンドで **同じ値** を使う。
バックエンドが JWT を復号するときに同じ鍵が必要なため。

---

#### 2. `frontend/src/lib/auth.ts` — NextAuth.js の設定

NextAuth.js の中枢。「どの方法でログインするか」「JWT に何を入れるか」を定義する。

```typescript
export const { handlers, auth, signIn, signOut } = NextAuth({
  providers: [Google],        // Google ログインを使う
  session: { strategy: 'jwt' }, // セッションを DB でなく JWT で管理する

  callbacks: {
    jwt({ token, user }) {
      // 初回ログイン時: Google から受け取ったユーザー情報を JWT に追加
      if (user) {
        token.email = user.email
        token.name = user.name
      }
      return token  // この token が暗号化されてクッキーに保存される
    },
    session({ session, token }) {
      // session.user.id をセットする（フロントエンドから使うため）
      if (token.sub) session.user.id = token.sub
      return session
    },
  },
})
```

ここからエクスポートされる4つの関数の役割：
| 関数 | 役割 |
|---|---|
| `handlers` | NextAuth が受け取る HTTP リクエストを処理する関数群 |
| `auth` | サーバーコンポーネントでセッション（ログイン情報）を取得する |
| `signIn` | ログイン処理を実行する |
| `signOut` | ログアウト処理を実行する |

---

#### 3. `frontend/src/app/api/auth/[...nextauth]/route.ts` — 認証エンドポイント

```typescript
import { handlers } from '@/lib/auth'
export const { GET, POST } = handlers
```

たった2行のファイル。
NextAuth.js は内部で `/api/auth/callback/google` などのエンドポイントを自動生成する。
このファイルはそれを Next.js の App Router に接続するだけのもの。

`[...nextauth]` というフォルダ名の `...` は「何でも受け取る」という意味（スプレッドルート）。
`/api/auth/signin` も `/api/auth/callback/google` も全部このファイルで処理する。

#### 4. `frontend/middleware.ts` — 未ログインユーザーをブロック

```typescript
export default auth((req) => {
  if (!req.auth) {
    // ログインしていなければトップページへリダイレクト
    return Response.redirect(new URL('/', req.url))
  }
})

export const config = {
  // このミドルウェアを適用するページのパターン
  matcher: ['/dashboard/:path*', '/weight/:path*', '/meal/:path*', '/exercise/:path*'],
}
```

**ミドルウェア** とはページが表示される前に必ず実行される処理のこと。
`matcher` に指定したページへのアクセスがあるたびに `req.auth`（ログイン状態）を確認する。
未ログインなら `/` にリダイレクト、ログイン済みならそのままページを表示する。

#### 5. `frontend/src/lib/api-client.ts` — バックエンドへ JWT を送る関数

```typescript
export async function apiFetch(path: string, options?: RequestInit) {
  const cookieStore = await cookies()

  // クッキーから NextAuth が保存した JWT を取り出す
  const token =
    cookieStore.get('authjs.session-token')?.value ??
    cookieStore.get('__Secure-authjs.session-token')?.value

  return fetch(`${API_URL}${path}`, {
    ...options,
    headers: {
      'Content-Type': 'application/json',
      // JWT を Authorization ヘッダーに付けて送る
      ...(token ? { Authorization: `Bearer ${token}` } : {}),
    },
  })
}
```

フロントエンドからバックエンドに API リクエストを送るとき、
「自分がログイン済みであること」をバックエンドに証明する必要がある。
そのために JWT を `Authorization: Bearer <トークン>` というヘッダーに付けて送る。

バックエンドはこのトークンを復号して「誰のリクエストか」を確認する。

---

#### 6. `frontend/src/types/next-auth.d.ts` — TypeScript の型拡張

```typescript
declare module 'next-auth' {
  interface Session {
    user: {
      id: string  // ← これを追加
    } & DefaultSession['user']
  }
}
```

NextAuth のデフォルトでは `session.user.id` という型が定義されていない。
このファイルで「`Session` には `id` フィールドがある」と TypeScript に教えることで、
コード上で `session.user.id` を型エラーなく使えるようになる。

#### 7. `backend/src/middleware/auth.ts` — バックエンドでの JWT 検証

```typescript
export const authMiddleware = createMiddleware(async (c, next) => {
  // ① Authorization ヘッダーからトークンを取り出す
  const token = c.req.header('Authorization')?.slice(7)  // "Bearer " の7文字を除く

  // ② AUTH_SECRET から復号キーを導出（NextAuth と同じアルゴリズム）
  const derivedKey = getDerivedKey(process.env.AUTH_SECRET!)

  // ③ JWE（暗号化された JWT）を復号してユーザー情報を取り出す
  const { payload } = await jwtDecrypt(token, derivedKey)

  // ④ メールアドレスでユーザーを検索、存在しなければ新規作成
  const user = await prisma.user.upsert({
    where: { email: payload.email },
    create: { email, name, image },
    update: { name, image },
  })

  // ⑤ 後続の処理で使えるように userId をコンテキストにセット
  c.set('userId', user.id)
  await next()
})
```

**なぜ `hkdfSync` で鍵を導出するのか？**
NextAuth は JWT を暗号化するときに `AUTH_SECRET` をそのまま使わず、
HKDF という関数で変換した鍵を使う。
バックエンドも同じ変換をしないと復号できないため、同じ処理を書いている。

**`upsert` とは？**
`update` + `insert` を合わせた造語。
「メールアドレスが存在すれば更新、なければ新規作成」を1回の処理で行う。
初回ログイン時は users テーブルにレコードがないため、自動的に作成される。

#### 8. `frontend/src/app/page.tsx` — ログインページ

デザインシステムに沿ったログインページを実装。

```typescript
<form action={async () => {
  'use server'               // ← Server Action（サーバーで実行される関数）
  await signIn('google', { redirectTo: '/dashboard' })
}}>
  <button type="submit">Google でログイン</button>
</form>
```

`'use server'` はこの関数がサーバー側で実行されることを Next.js に伝えるディレクティブ。
ボタンを押すとサーバー側で `signIn('google')` が呼ばれ、Google の認証画面にリダイレクトされる。

---

### ハマった点・補足

- **`types: ["node"]` を `tsconfig.json` に追加**: TypeScript が `process.env` や `node:crypto` を認識できなかったため追加
- **クッキー名**: NextAuth v5 では `authjs.session-token`（開発環境）と `__Secure-authjs.session-token`（本番環境）の2種類があり、両方確認する必要がある
- **JWE vs JWS**: NextAuth のトークンは署名だけの JWS ではなく暗号化された JWE 形式。バックエンドでの検証には `jwtDecrypt` が必要（`jwtVerify` では不可）

---

### 確認したこと

- `http://localhost:3000` でログインページが表示されること
- 「Google でログイン」でログインできること
- ログイン後に `/dashboard` へリダイレクトされること
