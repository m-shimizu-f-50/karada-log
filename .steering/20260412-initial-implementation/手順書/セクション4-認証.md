# セクション4: 認証（NextAuth.js・Google ログイン）

## このセクションで作るもの

- Google アカウントでログイン・ログアウトできる
- ログインしていないユーザーが `/dashboard` などにアクセスするとトップページに戻される
- ログイン後、バックエンド API にリクエストするとき「誰からのリクエストか」をバックエンドが確認できる

---

## 前提知識

### 認証と認可の違い

| 用語 | 意味 | 例 |
|---|---|---|
| **認証**（Authentication） | 「あなたは誰ですか？」を確認する | Google アカウントでログインする |
| **認可**（Authorization） | 「あなたはこれをしていいですか？」を確認する | 自分の記録だけ削除できる |

### OAuth 2.0 とは

パスワードを預からずに「Google が本人確認済み」という情報を受け取る仕組み。

```
① ユーザーが「Googleでログイン」をクリック
   ↓
② アプリが Google に「このユーザーを確認してください」と依頼
   ↓
③ Google の画面でユーザーがログインして「許可する」をクリック
   ↓
④ Google がアプリに「確認できました。ユーザー情報はこちら」と返答
   ↓
⑤ アプリがユーザー情報（メール・名前・画像）を受け取る
```

アプリはユーザーのパスワードを一切知らない。Google が代わりに確認してくれる。

### JWT（JSON Web Token）とは

ユーザー情報を暗号化してひとつの文字列にまとめたもの。

中身のイメージ：
```json
{
  "email": "test@example.com",
  "name": "テスト太郎",
  "exp": 1714000000
}
```

この情報を `AUTH_SECRET` という秘密鍵で **暗号化** したものが JWT。
暗号化されているので、`AUTH_SECRET` を知らないと中身を読めないし改ざんもできない。

**JWE（JSON Web Encryption）とは？**
JWT の中でも「暗号化」を使ったもの。NextAuth.js v5 はこれを使っている。
単に署名だけの JWT（JWS）とは違い、暗号化されているので内容が外から読めない。

### セッションとは

「ログイン状態を保持する仕組み」のこと。

HTTP は本来「記憶がない」プロトコル（ステートレス）。
1回リクエストを送っても、次のリクエストでは「あなた誰ですか？」となってしまう。
セッションを使うことで「前回ログインした人と同じ人だ」と識別できる。

このプロジェクトでは JWT をブラウザのクッキーに保存することでセッションを実現している。

```
① ログイン時: JWT をクッキーに保存
② 次回アクセス時: クッキーの JWT をバックエンドが確認
③ JWTが有効 → ログイン済みとして処理
```

`API_URL` は fetch するときに使うが、クライアント側から実行する場合もあるため `NEXT_PUBLIC_` をつけた。

### `frontend/src/lib/auth.ts` — NextAuth.js の設定

NextAuth.js の中枢ファイル。「どの方法でログインするか」「JWT に何を入れるか」を定義する。

```typescript
import NextAuth from 'next-auth'
import Google from 'next-auth/providers/google'

export const { handlers, auth, signIn, signOut } = NextAuth({

  // ① どのログイン方法を使うか
  providers: [Google],
  // Google の認証情報は AUTH_GOOGLE_ID と AUTH_GOOGLE_SECRET を
  // 環境変数から自動で読む（明示的に書かなくていい）

  // ② セッションの管理方法
  session: { strategy: 'jwt' },
  // 'jwt': セッション情報を JWT（クッキー）に保存する（DB不要）
  // 'database': セッション情報をDBに保存する（Prisma アダプターが必要）

  // ③ コールバック（各処理の途中で実行される関数）
  callbacks: {

    // JWT が作成・更新されるたびに呼ばれる
    jwt({ token, user }) {
      if (user) {
        // 初回ログイン時のみ user オブジェクトが存在する
        // Google から受け取ったユーザー情報を JWT に追加する
        token.email = user.email
        token.name = user.name
        token.picture = user.image
      }
      return token
      // この token が暗号化されてクッキーに保存される
    },

    // セッション情報が取得されるたびに呼ばれる
    session({ session, token }) {
      if (token.sub) {
        session.user.id = token.sub
        // token.sub は NextAuth が自動で設定するユーザーID
        // session.user.id として使えるようにする
      }
      return session
    },
  },
})
```

**エクスポートされる4つの関数の役割：**

| 関数 | 何者か | どこで使うか |
|---|---|---|
| `handlers` | GET/POST のリクエストハンドラ | `app/api/auth/[...nextauth]/route.ts` |
| `auth` | セッション（ログイン状態）を取得する関数 | サーバーコンポーネント・ミドルウェア |
| `signIn` | ログイン処理を実行する関数 | ログインページのボタン |
| `signOut` | ログアウト処理を実行する関数 | ヘッダーのログアウトボタン |

### `frontend/src/app/api/auth/[...nextauth]/route.ts` — 認証エンドポイント

```typescript
import { handlers } from '@/lib/auth'

export const { GET, POST } = handlers
```

たった2行のファイル。でも重要な役割がある。

NextAuth.js は内部で以下のエンドポイントを自動で処理する：
- `/api/auth/signin` — ログインページへのリダイレクト
- `/api/auth/callback/google` — Google からのコールバック受け取り
- `/api/auth/signout` — ログアウト処理
- `/api/auth/session` — セッション情報の取得

このファイルが「これら全部を `handlers` に任せる」と接続している。

**`[...nextauth]` というフォルダ名の意味**
`[...]` は「何でも受け取る（キャッチオール）」という Next.js の記法。
`/api/auth/signin` も `/api/auth/callback/google` も、全部このファイルで処理される。

### `frontend/middleware.ts` — 未ログインユーザーをブロック

```typescript
import { auth } from '@/lib/auth'

export default auth((req) => {
  // req.auth にログイン情報が入っている
  // null = 未ログイン
  if (!req.auth) {
    const url = new URL('/', req.url)
    return Response.redirect(url)
    // トップページ（/）にリダイレクトする
  }
  // ログイン済みの場合は何もしない（そのままページが表示される）
})

// このミドルウェアを適用するページを指定
export const config = {
  matcher: [
    '/dashboard/:path*',  // /dashboard, /dashboard/xxx など
    '/weight/:path*',
    '/meal/:path*',
    '/exercise/:path*',
  ],
}
```

**ミドルウェアとは？**
ページが表示される前に必ず実行される「門番」のような処理。

```
ユーザーが /dashboard にアクセス
        ↓
middleware.ts が実行される
        ↓
ログイン済み？ → YES → ダッシュボードを表示
             → NO  → / にリダイレクト
```

**`matcher` とは？**
ミドルウェアを適用するパスのパターン。
`/dashboard/:path*` は「`/dashboard` で始まるすべてのパス」という意味。
ここに含まれないパスでは middleware は実行されない。

### `frontend/src/lib/api-client.ts` — バックエンドへ JWT を送る関数

```typescript
import { cookies } from 'next/headers'

const API_URL = process.env.NEXT_PUBLIC_API_URL ?? 'http://localhost:8080'

export async function apiFetch(path: string, options?: RequestInit) {
  const cookieStore = await cookies()
  // ↑ サーバー側でクッキーを読む Next.js の関数

  // NextAuth v5 がクッキーに保存する JWT を取り出す
  // 開発環境と本番環境でクッキー名が異なるため両方確認する
  const token =
    cookieStore.get('authjs.session-token')?.value        // 開発環境
    ?? cookieStore.get('__Secure-authjs.session-token')?.value  // 本番環境（HTTPS）

  return fetch(`${API_URL}${path}`, {
    ...options,  // 呼び出し元から渡されたオプション（method, body など）
    headers: {
      'Content-Type': 'application/json',
      // JWT があれば Authorization ヘッダーに付ける
      ...(token ? { Authorization: `Bearer ${token}` } : {}),
      ...options?.headers,  // 呼び出し元から渡されたヘッダー
    },
  })
}
```

**なぜ JWT をヘッダーに付けるのか？**
バックエンドは「このリクエストが誰から来たのか」を知る必要がある。
クッキーはブラウザが自動で送るが、フロントエンドのサーバー → バックエンドの通信には含まれない。
そのため、クッキーから JWT を取り出して `Authorization: Bearer <JWT>` というヘッダーに手動で付ける。

**`Bearer` とは？**
Authorization ヘッダーの認証方式のひとつ。
「このトークンを持っていれば（Bearerすれば）アクセスできる」という意味から来ている。

```
Authorization: Bearer eyJhbGciOiJkaXIi...（JWT の文字列）
```

**`?.value` とは？**
オプショナルチェーン（Optional Chaining）。
`cookieStore.get('...')` が `undefined` を返した場合でも、
エラーを起こさずに `undefined` を返してくれる。

### `frontend/src/types/next-auth.d.ts` — TypeScript の型拡張

```typescript
import { DefaultSession } from 'next-auth'

declare module 'next-auth' {
  interface Session {
    user: {
      id: string  // ← id フィールドを追加
    } & DefaultSession['user']
    // ↑ DefaultSession['user'] は NextAuth のデフォルトの型
    //   & は「この型とマージする」という意味

```

**なぜこのファイルが必要か？**

```typescript
const session = await auth()

// NextAuth のデフォルト型には id がない
```

### `backend/src/middleware/auth.ts` — バックエンドでの JWT 検証

バックエンドが受け取った JWT を復号して「誰からのリクエストか」を確認するミドルウェア。

```typescript
import { createMiddleware } from 'hono/factory'
import { hkdfSync } from 'node:crypto'  // Node.js の暗号化モジュール
import { jwtDecrypt } from 'jose'        // JWT の復号ライブラリ
import { prisma } from '../lib/db.js'

export type AuthVariables = {
  userId: string
  // ↑ このミドルウェアが後続の処理に渡す値の型
}

// AUTH_SECRET から暗号化キーを導出する（NextAuth と同じアルゴリズム）
function getDerivedKey(secret: string): Uint8Array {
  return new Uint8Array(
    hkdfSync(
      'sha256',                              // ハッシュアルゴリズム
      secret,                                // 元となる秘密鍵
      '',                                    // ソルト（空）
      'Auth.js Generated Encryption Key',    // 用途を示す文字列
      32                                     // 出力する鍵の長さ（バイト）
    )
  )
}
```

**HKDF（HMAC-based Key Derivation Function）とは？**
元の秘密鍵から、特定の用途向けの派生鍵を生成する関数。
NextAuth は `AUTH_SECRET` をそのまま暗号化キーとして使わず、
HKDF で変換してから使う。バックエンドも同じ変換をしないと復号できない。

```typescript
export const authMiddleware = createMiddleware<{ Variables: AuthVariables }>(
  async (c, next) => {

    // ① Authorization ヘッダーを取得
    const authHeader = c.req.header('Authorization')
    if (!authHeader?.startsWith('Bearer ')) {
      return c.json({ error: '認証が必要です' }, 401)
      // ヘッダーがなければ 401 Unauthorized を返す
    }

    const token = authHeader.slice(7)
    // "Bearer " の7文字を除いた部分が JWT

    try {
      // ② JWT を復号
      const derivedKey = getDerivedKey(process.env.AUTH_SECRET!)
      const { payload } = await jwtDecrypt(token, derivedKey)
      // payload に { email, name, picture, ... } が入っている

      const email = payload.email as string
      const name = payload.name as string | undefined
      const picture = payload.picture as string | undefined

      // ③ ユーザーをDBで取得 or 新規作成
      const user = await prisma.user.upsert({
        where: { email },
        // メールアドレスでユーザーを検索

        create: { email, name, image: picture },
        // 存在しなければ新規作成（初回ログイン時）

        update: { name, image: picture },
        // 存在すれば名前・画像を更新
      })

      // ④ 後続の処理（ルートハンドラ）に userId を渡す
      c.set('userId', user.id)
      await next()
      // next() を呼ぶことで次の処理（実際のルートハンドラ）に進む

    } catch {
      return c.json({ error: '認証が無効です' }, 401)
      // 復号に失敗したら 401 を返す（トークンが偽造・期限切れ）
    }
  }
)
```

**`upsert` とは？**
`update`（更新）+ `insert`（挿入）の造語。
「存在すれば更新、なければ新規作成」を1回の処理で行う。

```typescript
prisma.user.upsert({
  where: { email },   // この条件で検索
  create: { ... },    // 見つからなければ作成
  update: { ... },    // 見つかれば更新
})
```

**`c.set()` / `c.get()` とは？**
Hono のコンテキストに値を保存・取得する方法。
ミドルウェアから後続のルートハンドラに値を渡すときに使う。

```typescript
// ミドルウェア（auth.ts）
c.set('userId', user.id)

// ルートハンドラ（routes/weight.ts など）
const userId = c.get('userId')  // ← ミドルウェアが設定した値を取得
```

## 全体の認証フロー

```
【ログイン時】

ユーザーが「Googleでログイン」をクリック
    ↓
Server Action が signIn('google') を呼ぶ
    ↓
Google の認証画面にリダイレクト
    ↓
ユーザーが Google で許可
    ↓
Google から /api/auth/callback/google にリダイレクト
    ↓
NextAuth が jwt コールバックを実行（email・name を JWT に追加）
    ↓
JWT を暗号化してクッキー（authjs.session-token）に保存
    ↓
/dashboard にリダイレクト
```

```
【保護ページへのアクセス時】

ユーザーが /dashboard にアクセス
    ↓
middleware.ts が実行される
    ↓
クッキーの JWT を確認 → ログイン済み → /dashboard を表示
                      → 未ログイン → / にリダイレクト
```

```
【バックエンド API へのアクセス時】

フロントエンドが apiFetch('/api/weight') を呼ぶ
    ↓
クッキーから JWT を取り出す
    ↓
fetch に Authorization: Bearer <JWT> ヘッダーを付ける
    ↓
バックエンドが JWT を受け取る
    ↓
authMiddleware が JWT を復号（HKDF で鍵を導出 → jwtDecrypt）
    ↓
email でユーザーを upsert（初回は新規作成）
    ↓
c.set('userId', user.id) で後続の処理に渡す
    ↓
実際のルートハンドラが userId を使ってDBを操作
```

## ハマった点・補足

- **Prisma 7 の `tsconfig.json` に `"types": ["node"]` が必要**: `process.env` や `node:crypto` を TypeScript が認識できなかったため追加した
- **NextAuth v5 のクッキー名**: v4 では `next-auth.session-token` だったが、v5 から `authjs.session-token` に変わった。開発環境（HTTP）と本番環境（HTTPS）でも名前が異なる（`__Secure-` プレフィックスの有無）
- **JWE の復号に HKDF が必要**: NextAuth は JWT を暗号化するとき `AUTH_SECRET` をそのまま使わず、HKDF で変換した鍵を使う。バックエンドでも同じ変換をしないと復号できない。`jose` ライブラリの `jwtDecrypt` と Node.js の `hkdfSync` を組み合わせて実現した
