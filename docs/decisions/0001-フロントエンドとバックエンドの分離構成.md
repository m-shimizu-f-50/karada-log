# ADR-0001: フロントエンドとバックエンドを分離した構成を採用

- 日付: 2026-05-10
- 状態: 承認済み

## 背景

Next.js にはフロントエンドとバックエンド（API Routes）を同一プロジェクトで管理できる機能がある。
当初はこのフルスタック構成を検討していたが、バックエンドを Node.js で独立して開発したいという要件が生まれた。

## 検討した選択肢

### A. Next.js フルスタック構成（API Routes）

```
karada-log/
└── src/
    ├── app/          # フロントエンド（画面）
    └── api/          # バックエンド（API Routes）
```

**メリット**
- 1つのプロジェクトで完結するためシンプル
- Vercel へ1回のデプロイで完結
- フロントエンドとバックエンドで型定義を自然に共有できる
- 学習コストが低い

**デメリット**
- バックエンドが Next.js の仕組みに縛られる
- Node.js の純粋なサーバー開発スキルが身につきにくい

### B. フロントエンド・バックエンド分離構成

```
karada-log/
├── frontend/   # Next.js（画面のみ）
└── backend/    # Node.js API サーバー
```

**メリット**
- フロントエンドとバックエンドの責務が明確に分かれる
- バックエンドを Node.js として独立して学べる
- 実務でよく見られるアーキテクチャに近い形で経験を積める
- 将来的にバックエンドを別言語（Go など）に置き換えやすい

**デメリット**
- デプロイが2つになる（フロントエンド + バックエンド）
- CORS の設定が必要になる
- フロントエンドからバックエンドへの API 呼び出し時に認証トークンの受け渡しが必要
- 学習コストが上がる

## 決定

**B. フロントエンド・バックエンド分離構成**を採用する。

## 理由

- バックエンドを Node.js で独立して学ぶことが目的の一つである
- 実務に近い構成で開発経験を積むことを優先する
- フロントエンドとバックエンドの責務を明確に分けることで、それぞれの役割と設計を深く理解できる

## トレードオフ・注意点

- Render（バックエンド）と Vercel（フロントエンド）の2つのデプロイ先を管理する必要がある
- フロントエンドからバックエンドへのリクエスト時に CORS とJWT の設定が必要
- ローカル開発時はフロントエンドとバックエンドを同時に起動する必要がある
